# Phase 5.1 — Performance audit

Date: 2026-05-29
Auditor: Claude agent (Task 5.1)

## Executive summary

Code-read-only audit of services + key pages + recent migrations. Most paths
are reasonably well-batched (Promise.all, bulk lookups with IN(...)), and the
recent service additions clearly try to dodge N+1s. The real exposure is
concentrated in three places: (a) the weekly-reports cron and the bulk-
reminder loop both fan out *per-student* synchronous notification calls,
(b) the dashboard + batch-detail pages run several full scans over
`vw_attempts_legacy` (a UNION ALL view over 28k+-row legacy tables) which is
the single most likely 10s-timeout candidate, and (c) several `IN (?, ?, ?,
…)` lists are constructed with no upper bound on the input cardinality
(orgs with thousands of students will eventually trip MySQL's
`max_allowed_packet` or the planner).

**Top 3 findings (severity-ranked):**
1. F1 — Dashboard average-score + activity-feed queries scan `vw_attempts_legacy` via a `studentId IN (SELECT … JOIN …)` correlated against the UNION-ALL view. Highest 10s-timeout risk.
2. F2 — Weekly-reports cron fans out `processOne(...)` serially in nested `for`-loops with per-student notification roundtrips inside the request lifecycle.
3. F3 — Bulk-reminder loop calls `sendNotificationBroadcast` in an `await`-per-student inner loop with no concurrency cap.

## DB query findings (priority order)

### F1 — Dashboard scans `vw_attempts_legacy` twice with a sub-SELECT JOIN against tq_batch_enrollments
**Severity**: HIGH
**Surface**: `src/lib/services/dashboard.service.ts` (the two `$queryRaw` blocks at ~L91–100 and L110–131)
**Symptom**: Both the "avg score" and "recent activity" queries do
`WHERE a.studentId IN (SELECT DISTINCT studentId FROM tq_batch_enrollments tbe JOIN tq_batches tb …)`. `vw_attempts_legacy` is a `UNION ALL` over `main_exam_status` + `practice_exam_status` (both 28k+ rows per CLAUDE.md). MySQL frequently materialises views before applying `WHERE`, which means every dashboard load touches the full union.
**Impact**: At scale (or even mid-tier orgs with many students), this is the single most likely query to brush the Hostinger 10s `max_statement_time` ceiling. Each render runs *both* queries; nothing is cached.
**Recommended fix**: (a) Materialise the student-id list in app code first (`prisma.batchEnrollment.findMany({ where: { batch: { orgId }, isActive: true }, select: { studentId: true } })`) then pass an explicit `IN (?, ?, …)`; (b) add a SQL-level filter on `finishedAt >= NOW() - INTERVAL 90 DAY` for the average row (the spec says "weighted average" but the time-window isn't enforced — older finished attempts dominate and there's no need to scan them); (c) consider caching the dashboard payload for ~60s.
**Estimated effort**: M

### F2 — Weekly-reports cron is fully serial across orgs × batches × students
**Severity**: HIGH
**Surface**: `src/lib/services/weekly-report-cron.service.ts::runWeeklyReports` (L140–217)
**Symptom**: Three nested `for` loops (`orgs → batches → enrollments`). Each iteration awaits `processOne`, which itself awaits `buildParentReport` (5+ DB roundtrips and a `renderToBuffer` PDF render), then awaits notification broadcast, then awaits a `weeklyReportRun.create`. Default `limit = 200` but they execute strictly sequentially.
**Impact**: Even at 200 students × ~3s per student (PDF + 3 notification channels), that's a 10-minute single-invocation runtime — well beyond a Vercel serverless function ceiling. On Hostinger DB the per-loop pattern also keeps a long-lived connection slot busy.
**Recommended fix**: (a) Parallelise per-student with `pLimit(4..8)` inside each batch; (b) move PDF rendering + notification dispatch to a background queue (BullMQ / a separate worker route invoked per-tuple); (c) drop the `weeklyReportRun.findUnique` pre-check and rely solely on the P2002 catch — saves one roundtrip per student.
**Estimated effort**: L

### F3 — `sendBulkReminders` awaits notification dispatch per-student in a tight loop
**Severity**: HIGH
**Surface**: `src/lib/services/bulk-reminder.service.ts::sendBulkReminders` (L193–240, especially the `for (const sid of notStarted)` block calling `await sendNotificationBroadcast`)
**Impact**: With the 100-assignment cap and 30+ enrollees each, a single call can serialise 3,000+ HTTP roundtrips to whatsapp/sms providers — the request will time out on Vercel before the loop finishes.
**Recommended fix**: Collect the per-student dispatch payloads and run them through a concurrency-limited pool (e.g. `p-limit` 8–16). Better: enqueue and return immediately; UI polls status.
**Estimated effort**: M

### F4 — `assignment.service.createAssignment` notifies students sequentially
**Severity**: MEDIUM
**Surface**: `src/lib/services/assignment.service.ts::createAssignment` (L116–132 — `for (const s of students) await sendNotificationBroadcast(...)`)
**Impact**: Owner clicks "Assign" → waits for N students × 2 channels of synchronous HTTP. Acceptable for batches of 10–20; painful at 100+. Compounded by `createBulkAssignments` which calls this serially per batch.
**Recommended fix**: Same fix as F3 — concurrency-limited pool. Bonus: fire the broadcast off as background work and return assignment id immediately.
**Estimated effort**: M

### F5 — `loadStudentResultsBreakdown` UNION-ALLs two legacy tables with no index hint on `token`
**Severity**: MEDIUM
**Surface**: `src/lib/services/parent-report.service.ts::loadStudentResultsBreakdown` (L154–180)
**Symptom**: `SELECT … FROM main_exam_result WHERE token IN (...) UNION ALL SELECT … FROM practice_exam_result WHERE token IN (...) LEFT JOIN vw_questions LEFT JOIN vw_subjects LIMIT 5000`. The `LIMIT` is applied *after* the join. With 28k+ legacy result rows per table and no guaranteed index on `token`, this scan is unbounded.
**Impact**: A student with many attempts can blow past 10s. Even with the limit, the planner must materialise the union before joining.
**Recommended fix**: (a) Verify a legacy index exists on `main_exam_result.token` and `practice_exam_result.token` (add it via raw ALTER if missing — only safe schema change to a legacy table); (b) consider splitting into two queries instead of UNION ALL so each side can use its own index.
**Estimated effort**: S (index add) + S (split)

### F6 — `question-bank.importQuestionsFromXlsx` runs serial `createQuestion` + `orgQuestion.create` per row
**Severity**: MEDIUM
**Surface**: `src/lib/services/question-bank.service.ts::importQuestionsFromXlsx` (L111–146)
**Impact**: A 500-row import (the cap) does ~1000 DB roundtrips serially. On Hostinger latency (~30–60ms/query) that's 30–60s before the import returns — likely tripping Vercel's 60s function ceiling.
**Recommended fix**: (a) Batch validate subjects with one `IN (?, ?, …)` upfront; (b) batch the legacy inserts (chunks of 50) and the `orgQuestion.createMany`; (c) stream a progress response or move to background.
**Estimated effort**: M

### F7 — `dashboard.service` always issues a separate `vw_classes` lookup + a separate `vw_students` lookup for owner name
**Severity**: LOW
**Surface**: `src/lib/services/dashboard.service.ts` (L141–157)
**Symptom**: Two `$queryRawUnsafe` calls run sequentially *after* the `Promise.all`; could ride along inside it.
**Recommended fix**: Include `vw_classes` and the owner name lookup in the `Promise.all` block at L65.
**Estimated effort**: S

### F8 — `searchTestsForPicker` runs two correlated subqueries per row (totalMarks + questionCount)
**Severity**: MEDIUM
**Surface**: `src/lib/services/assignment.service.ts::searchTestsForPicker` (L200–212)
**Symptom**: `SELECT … (SELECT SUM(q.marks) FROM vw_test_questions q WHERE q.testId = t.id) AS totalMarks, (SELECT COUNT(*) FROM vw_test_questions q WHERE q.testId = t.id) AS questionCount`. Two correlated subqueries against a view per result row, with `LIMIT 60` and a `NOT EXISTS (SELECT 1 FROM tq_org_tests …)`.
**Impact**: Hostinger statement-time pressure when the underlying `main_exam_to_question` table grows; the CLAUDE.md gotcha explicitly warns against correlated subqueries on 28k-row queries.
**Recommended fix**: One JOIN with `GROUP BY t.id` and aggregates, or precompute totalMarks on `vw_tests`.
**Estimated effort**: M

### F9 — `searchQuestions` adds a correlated COUNT subselect per row for option count
**Severity**: LOW
**Surface**: `src/lib/services/question-bank.service.ts::listOrgQuestions` (L336–345) and `src/lib/services/test-builder.service.ts::searchQuestions` (L141–149)
**Symptom**: `(SELECT COUNT(*) FROM vw_question_options o WHERE o.questionId = q.id) AS optionCount` per row. With pagination at 60/page this is bounded but still 60 sub-queries.
**Recommended fix**: Replace with `LEFT JOIN vw_question_options … GROUP BY q.id` or accept count=4 fallback (every supported type is 4-option MCQ except fill-in-blank).
**Estimated effort**: S

### F10 — `addStudentsToBatch` is O(roster) sequential, with email lookup per row against legacy `student`
**Severity**: MEDIUM
**Surface**: `src/lib/services/batch.service.ts::addStudentsToBatch` (L161–214)
**Symptom**: For each roster entry, a `SELECT student_id FROM student WHERE email_address = …`, then a `createLegacyStudent`, then a 2-query `$transaction` (findUnique + create twice). A 100-row roster is 4–500 sequential queries.
**Impact**: Visible UI lag on imports; can timeout on Vercel.
**Recommended fix**: Bulk-lookup existing students by email IN(...), then bulk insert via `createMany` for `BatchEnrollment` + `OrgMembership` (Prisma supports `createMany` with `skipDuplicates: true` on MySQL via the unique constraints).
**Estimated effort**: M

### F11 — `batches/[id]` server page runs five legacy queries + a `vw_classes` lookup, all gated on a `studentIds` IN list with no upper bound
**Severity**: MEDIUM
**Surface**: `src/app/coaching/batches/[id]/page.tsx` (L46–79)
**Symptom**: The page builds `studentIds.map(() => "?").join(",")` lists for two GROUP BY queries against `vw_attempts_legacy`. A batch with 200+ students produces a long IN-list; MySQL's planner may fall back to a scan, and the response stays in the server-render critical path (no Suspense).
**Recommended fix**: (a) Cap the page at the first ~100 students and lazy-load the rest via the API; (b) wrap the heavy panels in `<Suspense>` and stream — first paint should show the header and roster, score history can pop in.
**Estimated effort**: M

## Page-level findings

### P1 — `/admin/organizations` is a fully client component
**Severity**: MEDIUM
**Surface**: `src/app/admin/(authenticated)/organizations/page.tsx` (whole file `"use client"`)
**Symptom**: Initial render shows skeleton → fetch → render. Filters, debounced search, etc. are client-side, but the *first* paint with current filters could be a server-rendered list. Pure SSR/Suspense version would feel instant on first navigation. Also ships the whole React form bundle to the client.
**Recommended fix**: Convert the list into a server component that accepts search params; keep only the filter form interactive (use `useRouter().replace` on change). Saves both bundle weight and first-paint time.
**Estimated effort**: M

### P2 — `loadDashboard` runs sequentially with two additional lookups *after* `Promise.all`
**Severity**: LOW (see F7)
**Surface**: `src/app/coaching/dashboard/page.tsx` + service
**Note**: Page-side itself uses Promise.all well; the addressable lag is in the service (F7).

### P3 — `/attempts/[id]` is a single `"use client"` page that fetches via a separate roundtrip
**Severity**: MEDIUM
**Surface**: `src/app/attempts/[id]/page.tsx` (L47–81, the load-on-mount `fetch`)
**Symptom**: User clicks "Start" → sees a `Loader2` until the API call returns. Test-taking UX is the most latency-sensitive route in the product. A server component fetch + hydrate would skip one network roundtrip.
**Recommended fix**: Split into a server component that loads the attempt and passes initial state via props to a much smaller client island. The huge state machine and timer logic must stay client, but the initial data shouldn't roundtrip.
**Estimated effort**: M

### P4 — `/tests` (student browse) re-fetches on every filter change without prefetching
**Severity**: LOW
**Surface**: `src/app/tests/page.tsx`
**Symptom**: Every filter toggle does a fresh GET; `/api/taxonomy` is also client-fetched.
**Recommended fix**: Render initial filter+test grid server-side; use URL search params for filter state so back/forward works and pages can be cached at the edge.
**Estimated effort**: M

### P5 — `lucide-react` icons imported in every client component (named imports)
**Severity**: LOW
**Surface**: All client pages — at least 8+ icons per page
**Symptom**: lucide-react named imports tree-shake reasonably in recent versions, but a quick grep shows the same heavy import shape (e.g. attempts/[id] imports 10 icons). Worth verifying the production bundle shows each icon as its own module.
**Recommended fix**: Confirm via `next build` analyzer; if regression, switch to `lucide-react/dist/esm/icons/<name>` imports.
**Estimated effort**: S

### P6 — No `<Image>` usage found in audit; `logoUrl` etc. rendered as `<img>`
**Severity**: LOW
**Surface**: Likely `src/components/brand/logo.tsx` and email-branding consumers (not opened in this pass)
**Note**: Flagging as a hot-spot to verify; org logos shown on every dashboard render should use `next/image` with `unoptimized: false` for the CDN path.
**Estimated effort**: S to verify, S to fix

## Index recommendations

| Table | Column(s) | Why |
|---|---|---|
| `tq_assignments` | `(orgId, isActive, createdAt)` | `bulk-reminder.previewBulkReminders` and `loadDashboard` both filter on `orgId + isActive + createdAt >= ?`. Schema has `@@index([orgId])` and `@@index([createdAt])` separately — a composite would let MySQL pick a single index. |
| `tq_assignments` | `(orgId, batchId, isActive)` | Per-batch active-assignment lookups (used by batch detail and bulk reminders). |
| `tq_batch_enrollments` | `(batchId, isActive)` | Every active-enrollment lookup filters by `batchId + isActive = true`. Current `@@unique([batchId, studentId])` covers batchId-only but `isActive` filtering still scans within the batch. |
| `tq_assignment_attempts` | `(assignmentId, studentId)` | `bulk-reminder` builds a `startedByAssignment` set keyed on `(assignmentId, studentId)` — composite index helps the dual filter. |
| `tq_weekly_report_runs` | `(orgId, studentId, batchId, weekKey)` | Already covered by the UNIQUE; OK. |
| `tq_org_questions` | `(orgId, isActive, createdAt)` | `listOrgQuestions` filters/sorts on all three. Schema has `@@index([orgId])` only. |
| `tq_org_tests` | `(legacyTestId, isActive, orgId)` | `searchTestsForPicker`'s `NOT EXISTS` subquery filters all three. |
| `tq_subscriptions` | `(orgId, status, createdAt)` | `loadDashboard`'s `findFirst` filters by `orgId + status IN (…) ORDER BY createdAt`. Three separate indices today; composite would help. |
| `main_exam_result` (legacy) | `token` | F5 — verify and add if missing (raw ALTER, only safe legacy schema touch). |
| `practice_exam_result` (legacy) | `token` | Same as above. |
| `student` (legacy) | `email_address` | `findByEmail` and roster import both hit it. Probably already exists but worth a check. |

## Things that look fine (sanity check)

- `bulk-assign.service.ts` — correctly pre-loads all batches in one query and validates org scope before iterating. Notification fan-out lives in `assignment.service` (flagged separately in F4), not here.
- `branding.service.ts` — single Prisma findUnique; not a hot spot.
- `subscription.service.ts` (not opened in detail) — used inside Promise.all calls, no obvious red flags from cross-references.
- `organization-hierarchy.service.ts` — small, query patterns look bounded.
- `parent-report.service.ts` rollups — `loadFinishedAttempts` correctly bulk-loads student + peers in a single query and splits in-memory. `LIMIT 2000` is the right defensive cap.
- Prisma `@@index` declarations on `tq_attempts` (legacy mirror) and `tq_batch_enrollments(studentId)` cover the common hot paths.
